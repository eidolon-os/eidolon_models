# d3通用提示增强A/B：局部有效，尚不支持默认替换

2026-10-19。用户要求保持提示内容框架，用通用引导提升澄清并验证泛化。本轮只比较一个固定追加段落与原提示，不根据中途结果修改；实际调用d3 **128次**、deepseek-v4-flash回复 **10次**，全部成功，无重试、训练或部署。

## 结论

**增加通用原则可以修复部分澄清错误，但本轮没有证明稳定、可迁移的整体提升。暂不把增强版替换为默认提示。**

增强版没有在本轮造成正确题退化；但增益只来自一个已知指代缺失场景的三个变体，新编场景、完整变体一致性和真实回复闭环均未显示额外收益。预登记的“旧、新两组都改善”条件未达到。本结果既不证明提示增强普遍无效，也不支持继续围绕剩余错题堆规则。

## 1. 实际改动与框架保持

只在`questions.move.instructions`原文尾部追加[这一段通用原则](PROMPT-ADDITION.txt)。保留原state、原指令、criteria内容与顺序、动作集合和回复生成任务。56对实际网络请求逐条校验，唯一差异确实为追加的instructions。

内容说明足够信息时直接回应、关键缺失且可询问时澄清、明确暂停或已问待答时等待、已完成时结束、无法作出允许决策时弃权。没有人物名、具体任务例句、case ID或按错误答案写的补丁。

“内容不写案例”不等于自动具备泛化能力，仍需由新场景的结果判断。

具体改善是旧“让他接着说”在原序、候选逆序、换名三种情况下由wait改为clarify。但选项逆序版本仍失败，因此这一场景没有达到全变体稳定。缺历史时主动澄清及已问澄清后的等待问题没有被该增强解决。

新编24题包含三候选、不同话题、开放回应、无关信息缺失不应追问、明确静默、请求已完成、问句但不是澄清、禁止clarify和用户补足信息。它们在已知失败类型之后由本地编写，属于拓展诊断，**不是盲测或独立真实用户泛化证据**。变体不是独立场景，不能把3条修复解释为3类问题都解决。

## 3. 真实回复文本闭环

两个策略分别运行3个新情境，每段由真实DeepSeek回复驱动后续d3决策；两个策略都3/3通过。

| 情境 | 原提示 | 增强提示 |
|---|---|---|
| 缺少回应者指向→澄清→用户指定→回复→结束 | 通过 | 通过 |
| 比较对象缺失→澄清→用户补充→回复→结束 | 通过 | 通过 |
| 明确要求通用建议、不需要追问→回复→结束 | 通过 | 通过 |

实际生成的澄清问题确实询问了希望哪位继续、两个选项分别是什么；用户补充后选中正确角色，完成后停止。普通明确请求没有被过度澄清。逐条阅读未发现任务顺序、角色选择或澄清对象明显偏离。

这次已经观察到真实“澄清→用户回答→恢复”的成功文本链路，但原提示也能完成，**不是增强带来的独有收益**。前次“让他接着说”的失败与本次“麻烦让那位继续介绍吧”的成功，使用了不同角色与表达，不能当成同题修复或归因于服务器变化；它反映需要继续关注表达敏感性。

用户后续回答是冻结脚本。两种策略的角色回复各自生成，文本可不同，闭环不是完全相同中间状态的因果对照；静态成对题才是本轮提示差异的主要证据。clarify后仍由驱动器直接等待，不依赖模型决定是否连续说话。没有生产Agent/TTS/真实设备或授权取消测试。

## 4. 输入与性能成本

静态56题的服务端报告输入token平均：原提示455.1，增强577.1，每题增加122 token，约26.8%。

| 静态请求 | 客户端p50 | 客户端p95 |
|---|---:|---:|
| 原提示 | 108.9 ms | 112.6 ms |
| 增强 | 121.4 ms | 128.8 ms |

耗时含HTTP与服务处理，非纯GPU；交替调用减轻时段偏差，但不是专门性能压测，不能把全部耗时差严格归因于提示长度。当前决策仍以质量为主；额外上下文有成本，不能仅因容量允许就不断加长。

## 5. 采用判断与停止

预登记条件：两组均改善、正常回应/停止/弃权无净退化、增强版3个闭环通过。后两项满足，第一项不满足。因此本轮不建议默认启用，不追加第二个提示版本，不追加测试预算以挑好结果。

后续若继续，优先保证“已执行clarify后等待用户”由已有运行时约束执行；不能把wait/abstain全局转换为clarify，也不能把所有信息缺失都当作必须澄清。需要在更独立的表达和真实业务分布上验证，才能声称具备泛化改善。本轮没有更改生产策略。
