# CosyVoice2 流式引擎

这是本机 TTS 的推理引擎。它以前只存在于板子上一份手工放置的副本里
（`/root/cv2/cpp`），没有 git、没有构建来源——也就是说它跑得通，但发布不了。
现在它在这里。

**为什么不交付二进制。** 它链接 `librknnrt` 和 `librkllmrt`，那是板子自己的 NPU
运行时；而一次发布是精确的 git commit。所以源码随发布走，`scripts/eidolon-tts-build`
在主机上就着它要链接的运行时编译一次。

**为什么有两个基准 .cpp 在这里。** `cosyvoice2_streaming_pipeline.cpp` 把
`cosyvoice2_rkllm_generate_test.cpp` 和 `cosyvoice2_hift_rknn_benchmark.cpp`
以文本方式 include 进两个命名空间（并把它们的 `main` 改名藏掉），
`embedded_rkllm::InitializeRkllm`、`embedded_hift::F0Bucket` 这些都来自那里。
它们是真实依赖，不是遗留物。把可复用的部分抽成正经头文件是应该做的，但那是另一
件事——先让它可发布。

## 服务模式

`--serve` 让它常驻：一行 stdin 一句话，PCM 从一个专用描述符流出。

昂贵的东西只付一次：RKLLM 主体（508 MB）、四张 RKNN 图、HiFT 的分桶、以及它们
的预热——合计约 2.9 秒。音色预计算（约 0.8 秒）也只付一次，见下一节。所以：

| | 每句起一个进程 | 常驻 |
|---|---|---|
| 加载 + 预热 | 2.9 s，每句 | 2.9 s，一次 |
| 音色预计算 | 0.8 s，每句 | 0.8 s，一次 |
| 首个 PCM | 2.1 s | 2.1 s |
| **调用方看到的首音** | **约 5.8 s** | 第一句 2.9 s，之后 **约 2.1 s** |

## 音色预计算的快照

音色预计算把 prompt 的前 28 个 token 喂给 encoder 和 Flow，把状态留在两者的 RKNN
cache 里；请求正是消费那份状态。它以前每句重做一次，只因为请求会把 cache 用掉，
而当时唯一的复位手段是 `Reset()`——把 cache 清零。

现在 `StreamingEncoder` 和 `StreamingFlow` 都能导出/导入 cache：进程内第一句跑完
预计算后存一份快照，之后每句写回去。cache 全都住在 `rknn_create_mem` 给的用户侧
缓冲里，`virt_addr` 上的字节就是状态本身，`rknn_mem_sync` 只做 cache 维护——不是
驱动侧的隐藏状态，所以存字节再写回去是可行的。实测每句从 0.8 s 降到 6–13 ms。

**一处不能一笔带过：预计算并非只依赖音色。** encoder 那半确实只吃 prompt token，
是纯音色的；但 Flow 那半还吃两块噪声（`flow_noise.Next(0)` / `Next(1)`），而取噪声
的生成器是跨句共享的、故意不复位的。所以基线里每句预计算用的噪声都不一样，快照
等于把 prompt 段的噪声钉在第一句那次抽取上。

这件事量过：只改 prompt 段噪声、其余全固定，mel 余弦 0.999975、MAE 0.034（mel 本身
std 3.23，约 1%）；波形对数谱余弦 0.994、MAE 0.417。而服务模式下基线与新实现第二句
的差异是对数谱余弦 0.989、MAE 0.428——同一个量级，说明差异**全部**来自那一次噪声
抽取。基线本来每句就在这个范围内抖，快照只是把它钉住，没有引入新的变化来源。

那两次 `Next()` 照样要取走再丢掉：生成器跨句共享，少抽两次会让后面每一块的噪声
错位，音频就真的变了。

**stdout 上为什么不是音频。** librkllm 在加载模型时往 stdout 打自己的横幅（实测
567 字节）。库不是我们的，改不了它写哪儿。所以服务模式在加载任何库之前先把
stdout 复制一份留给音频，再让 fd 1 指向 stderr：库照它的习惯写 stdout，写进的是
journal。指标和状态也走 stderr，用 `--- eidolon-tts ... ---` 哨兵括起来，库自己
的噪声就落在括号之外。

**一句失败不带走服务。** 模型还在内存里，拒绝的理由从 stderr 出去，下一句照常。

非服务模式的行为一个字节都没变——板上比对过：固定 `--seed` 时同一个二进制跑两遍
逐字节相同，加快照前后也逐字节相同（wav / mel / token 三个文件全等）。更强的一遍：
临时改一版，在预计算之后先 `Reset()` 清空再从快照恢复，输出仍与基线逐字节相同——
这说明恢复重建的就是预计算留下的那份状态，而不是靠残留状态蒙混过去。
