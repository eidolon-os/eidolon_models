# Jev 族零样本模型 vs 场景微调 laya：同一张卷子

日期：2026-10-08；10-09 补测 Kev-27B，10-10 补测 Perplexity 的 pplx-decider-v1.1-27B，10-12 补测 Cloudflare Clef 27B 与 AWS Strands Decider 2B，
并用 SGLang 重新服务 pplx 做对拍和压测（新增模型均 Apache-2.0，文章未收录）。性质：本地实测（A100 一张卡，依次跑）；候选全部零样本，没有训练任何候选，也没有改动 laya 模型。
起因：公众号横评《Jev类决策模型大横评：23个跑分，谁值得装》（2026-10-06）在它自建的 248 道中文短对话判定题上，
给出 laya 零样本 0.536、StartLux-Decision-27B 0.883、kev-4b 0.839、StartLux-Decision-9B 0.835（云端真 Jev 0.907）。
用户问：要不要换基座？场景训练过的 laya 比这些高分模型好还是差？那张榜量的是"不训就能用"的通用能力，
回答这个问题只能让它们在**我们封存的评测集**上零样本跑一遍，和已经训好的 laya 比。

## 结论

**边缘不换基座；但零样本大模型在参与决策上已经追平场景微调的 laya。** 端侧只放得下 laya，结论不变。
pplx-decider-v1.1-27B 是第一个零样本就能在一个场景上和 laya 打平的模型，家居上仍有明显差距。10-12 新测的两个都没超过它：
Clef 27B 两个场景都低于 pplx（参与决策端到端 90.5%、家居 89.2%），校准是零样本里最好的；Strands 2B 在我们的中文题上接近不可用（66.3%、56.7%）。
pplx 现在可以用 SGLang 主干服务，与官方实现逐题对拍 99.8% 首选项相同，吞吐是官方服务的 1.6–2 倍。

1. **参与决策 p-test 端到端**：pplx 96.0%、laya 95.1%；Kev-27B 94.0%、StartLux-27B 90.9%、Clef 90.5%、9B 88.6%、kev-4b 88.3%、Strands 2B 66.3%。
   只处理各自最有把握的 89.5%（laya 在 0.95 门槛的覆盖）时，pplx 99.1% / 应停却发言 1.2%，laya 97.1% / 0.7%，Kev-27B 97.3% / 3.4%。
   但不设门槛时 pplx 的应停却发言是 5.5%，laya 1.9%；在 p-dev 上 laya 仍领先（端到端 96.6% 对 95.0%，应停却发言 1.1% 对 8.0%）。
   两个集方向不一致，算打平，不算超过。
2. **家居续接 c-test**：argmax laya c4 98.0%；StartLux-27B 93.3%、pplx 92.8%、Kev-27B 90.6%、Clef 89.2%、9B 86.9%、kev 81.9%、Strands 2B 56.7%。
   laya 冻结阈值下接管 89.7%、错误执行 1。pplx 在同一阈值下接管 80.2%，但错误执行 7；在 c-dev 上任何阈值都做不到零错误执行（它对"不是客厅的那台"这类排除式说法以 0.97–0.99 的把握直接选另一台）。
   用 c-dev 上同一规则选阈值，StartLux-27B 接管 70.5%、错误执行 2，Kev-27B 接管 44.1%、错误执行 0。
   Clef 在冻结阈值下接管 71.9%、错误执行 7，要零错误执行得把门槛提到 0.99，接管只剩 12.9%。
3. **差距在产品约定，不在通用能力。** 4B 以上的零样本模型选人选几乎全对（99.4–100%，laya 97.2%），错在约定：角色已经把用户要的说完时判再有人发言
   （StartLux-27B 84 例、9B 104 例、Clef 68 例、Kev-27B 47 例、kev-4b 35 例、pplx 34 例，laya 10 例）；家居里排除式说法按约定应交还，零样本模型按常理推断后直接执行。
   这些约定是场景数据教会 laya 的，通用模型不知道。Strands 2B 例外：它在同一格错 263 例、人选也只有 91.8%，是能力不够，不只是约定不符。
4. **部署**：27B 级 bf16 要 50–75 GB 显存。A100 上单请求 p50 家居 / 参与决策：pplx 106 / 382 ms（SGLang 85 / 304 ms），Clef 104 / 195 ms，
   Kev-27B 103 / 185 ms，StartLux-27B 86 / 301 ms；Strands 2B 60 / 123 ms、4.6 GB。
   pplx 官方服务一次只处理一个请求、忙时直接拒绝，参与决策吞吐只有每秒 2.6 个；改用 SGLang 主干后饱和在每秒 4.2 个，Clef 7.1 个。
   SGLang 对拍官方实现 8,653 道题 99.8% 首选项相同，所以"pplx 必须自己写服务层"不再成立；但正式版还没包含这个改动，要从源码装。
   Strands 官方服务不能并发（并发 8 会让 CUDA 上下文报废），只能前面加队列。StartLux 权重 CC BY-NC 不能商用，其余新旧候选都是 Apache-2.0。
   laya 在 A100 上 2.1 GB、15 / 27 ms，在 RK3588 NPU 上线上实测家居续接 294–311 ms、参与决策 838 ms。**Eidolon 里 laya 仍跑在边缘。**
5. **可以借的**：若要云端老师或兜底，pplx 许可干净、零样本最强、附训练源码、SGLang 可服务，是首选；StartLux-27B 设备选择好但受许可限制；
   Clef 校准最好、多题一次预填更省算力，但两个场景都不如 pplx，又没有训练代码，只适合当第二老师。
   pplx 的训练集没有公开（只有清单和哈希），但训练代码与超参完整，可以用我们的场景数据在它上面微调，代价是 27B 全参训练的算力。

这和 [底座选型](base-selection-20260925.md)、[快速决策路线](eidolon-fast-decision-route-20260927.md) 的方向一致：端侧走 laya 加自有数据，大模型只当老师或上限参照。

## 技术先进性、开放性与掌控度

### 技术先进性

| | 架构与读出 | 训练规模 | 工程实现 | 结构性短板 |
|---|---|---|---|---|
| pplx-decider-v1.1 | 最新一代底座；全注意力层改为**非因果**（双向读整段状态），线性注意力层保持原样，相当于把生成式大模型改造成判别式编码器；255 行决策头取自词表行；校准温度；多模态 | 62.6 万条，1 轮全参，8 卡 | 只提供参考实现：一次一个请求，忙时拒绝 | 非因果使前缀无法缓存，同一状态的每个问题都整段重算（三题的参与决策 p50 382 ms，一题的家居 106 ms）；本地输入 8K |
| Clef | Qwen3.8-27B 底座保持因果；所有题和选项一次排在状态后面、只预填一遍；联合 schema 头（2 层证据路由 + 4 层题间自注意力，宽 1,024）给每个选项打分；多模态（图、视频） | 底座冻结，秩 256 LoRA 加头；内部合成数据，规模未公开；损失含 Brier 项 | SGLang 主干原生支持，另附参考实现 | 在我们的题上不如 pplx；没有训练代码 |
| Kev（4B / 27B） | 因果注意力加指针头；4B 是冻结底座上的 LoRA，27B 全参 | 4B 约 1 万条公开数据加生成的策略样本；27B 8 张 H200 训 16 小时 | 最成熟：同一状态多题共享前缀缓存、CUDA graphs、融合内核、MLX 后端、64K 验证 | 4B 零样本能力明显弱于 27B 级 |
| Strands Decider 2B | Qwen3.5-2B-Base 上秩 48 LoRA 加指针头，因果、共享前缀，按题型温度；三个种子的权重平均 | 24.7 万条公开数据为主，gemma-4-31B-it 软标签，KL 锚定上一版 | 代码仓完整，CPU / MPS / MLX / CUDA 都能跑；官方服务不能并发 | 2B 底座，在中文场景题上零样本接近不可用 |
| StartLux（9B / 27B） | 最朴素：在答案位置读选项字母的语言模型概率，按题型温度；26 个选项以上分组近似 | 未公开；训练数据含 Decision Index 中 14 个基准的训练集，自报指数部分属同分布 | 长输入分块预填与前缀共享、GGUF 全档量化、视觉塔 | 靠尺寸和数据取胜，读出方式本身没有新东西 |
| laya | 上一代范式：编码器分类器，每选项一个标记，题型嵌入加分桶温度 | 我们的场景数据，单卡数小时 | 唯一能按长度静态分档导出到 NPU 的 | 底座能力上限低：零样本弱、训练长度 1K、选项共享 512 token |

判断：技术前沿是"大底座 + 判别式读出 + 大规模混合任务训练"，pplx 在注意力上走得最远，Clef 在读出头上走得最远（一次预填答完全部题），Kev 在工程上最成熟。laya 不先进，
但在两个场景里靠数据把差距补回来，而且是唯一能跑在边缘的。先进性不等于场景表现：本轮差距的根源是产品约定，不是模型代际。

结论：

1. **边缘**：只有 laya 同时满足能上板和完全自控，继续是唯一选择。
2. **云端老师或兜底**：pplx 零样本最强、许可干净，适合给 laya 打软标签。但只该用在它擅长且与我们约定一致的地方（人选、参与决策的动作），
   家居排除式说法这类与产品约定冲突的地方不能拿它当金标。
3. **需要一个我们能训的服务端模型时**（例如物流），掌控度最高的是 kev-4b / 9B：单卡可训、代码标准、配方公开。pplx 要等有多卡训练资源；
   推理已不再绑死在它自己的实现上，SGLang 主干可用。Strands 2B 配方更全、更便宜，但中文零样本起点太低，不替代 kev。
4. Clef 只作第二老师或对照；StartLux 只作研究对照。

## 错在哪

零样本模型的主要错误相同：**本轮请求已经完成，仍判有人要说话**（金标 finish、预测 respond）。典型一例：
用户问"你们谁给我说句打气的话"，一个角色说完，金标是本轮结束；StartLux-9B 以 0.86 的概率判还应有人接着说。
9B 的 51 个此类错误（p-test 第 0 变体）里 47 个发生在角色刚说完之后。这是"请求被满足就收住"的产品约定，
laya 从参与决策的场景数据里学会了，零样本模型按通用对话习惯倾向于继续。kev 另有 30 例相反方向（该回应却判结束）和 24 例把等待判成澄清。

pplx 在家居两个集上共 11 个错误执行，7 个是排除式说法：Agent 问"主卧空调、客厅空调，要哪一个？"，用户答"不是客厅的那台"，
pplx 以 0.99 选主卧空调。按常理这是对的，但产品约定排除式说法要交还重新理解、不直接执行，金标是"重新理解"。

家居里零样本模型差在"跟随"：用户在刚操作过的设备上接着说"关了吧""再调低点"时，是否就是对同一设备的明确操作。
这也是场景约定（什么算接着操作、什么算换目标或重新理解），c 系列训练的重点就在这里。

## 换服务引擎后结果是否一致

SGLang 在 10 月 8 日合入 PR #42645，原生支持 pplx 这类非因果决策检查点，也支持 Clef 的联合 schema 头。PyPI 正式版 0.5.21 早于这次合入，
所以用主干源码 `d62b9c2`（10-11）装在 A100 上，与各自的参考实现在同样四个集上逐题对拍（`parity.py`）：

| pplx-decider-v1.1-27B | 仓库自带 `autojev.server` | 8,653 | 99.80% | 0.0033 / 0.024 / 0.062 | 7 | p-test 端到端 96.0% → 95.9%，c-test 92.8% → 93.0% |

两者的 ECE、覆盖率、混淆格、最差家族都与参考实现一致到小数点后两位，正文用 SGLang 的数字。SGLang 在 A100 上没有官方验证（PR 只测了 GB300 和 H200），

## laya 在 GPU 上的精度

laya 的离线评测器在 A100 上与 Mac 存档逐题相同（p_top 差 ≤ 0.0001）。服务原先按上游 laya 在 CUDA 上 autocast bf16，
校准后概率最多偏 0.14，家居 c-test 冻结阈值下 1 个执行掉到门槛以下变成交还（接管 89.7% → 89.4%）。
温度和阈值都是按 fp32 输出校准的，所以 7378e62 在 torch 后端去掉了 autocast；重测后 A100 服务与 Mac 服务逐题相同（3630/3630），
门槛决定与存档一致。板上 NPU、Mac MPS、ECS CPU 都不走这段代码，行为不变。代价：A100 上参与决策 p50 从 20.0 ms 变为 27.0 ms，家居从 18.5 ms 变为 15.1 ms。
