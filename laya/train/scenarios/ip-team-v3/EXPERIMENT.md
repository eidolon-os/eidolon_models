# IP Team 文本决策 v3：场景与上下文窗口试验（2026-09-28）

## 问题

本轮输入只考虑 **text**：原始用户文本、真实已公开的角色文本、当前候选和约束。按 [Ensemble 产品场景](https://eidolon.aimanthor.com/ensemble/)验证点名、开放讨论、内容接力、同一成员续说、用户改目标、澄清、安静等待及结束讨论。每次模型只选 `respond:<候选 ID>`、`clarify:<候选 ID>`、`wait`、`finish` 或 `abstain`；最多一位成员发言。候选标识是每次请求内的稳定替身，不靠可能重复的展示名称解析。

v2 同时训练 move 与九类 task，冻结对照完整一步仅 8/66，且本身训练题准确率仅 160/520。本次受控拟合诊断用相同 16 条训练记录，10 轮后同记录逐题准确率 26/32，剩余 6 个错误全部是选错成员；说明训练能下降损失，但成员对应与跨家族泛化尚未解决。本轮聚焦下一步动作及成员；发言文本仍由角色模型生成。`respond` 的可选 instruction 和 `clarify` 的必需具体 instruction 尚无可靠生成机制，所以即使本试验通过也不等于可直接映射为完整 SDK `DecisionResult`。

## 上下文容量依据

产品演示为约四位成员逐步接话；当前 Agent 默认一轮回复预算为 8，传至多 64 条近期公开消息。SDK 的 64 条和候选最多 64 位是线协议边界，不是 Laya 能读懂的容量承诺。当前训练配置的原始 v2 数据最多只有 4 条消息。使用 r14 同款分词器与 Laya 实际 `build_sequence`，以原创文本构造以下非用户流量的长度压力样本：

| 文本状态 | 候选 / 消息 / 每条回复 / 每份角色说明 | 紧凑状态 tokens | 带选项总 tokens | 1024 | 2048 |
|---|---|---:|---:|---|---|
| 短请求 | 2 / 2 / 80 字 / 60 字 | 262 | 512 | 完整 | 完整 |
| 普通接话 | 4 / 4 / 120 字 / 100 字 | 719 | 941 | 完整 | 完整 |
| 默认预算压力 | 4 / 9 / 160 字 / 120 字 | 1534 | 1756 | 只保留 52% 状态 | 完整 |
| 长讨论 | 4 / 13 / 220 字 / 160 字 | 2653 | 2875 | 截断 | 截断 |
| 六位候选压力 | 6 / 9 / 160 字 / 120 字 | 1700 | 1946 | 截断 | 完整 |
| 线协议 64 条消息 | 4 / 64 / 160 字 / 120 字 | 9257 | 9479 | 截断 | 截断 |

当前 Laya 构造函数默认保留状态**开头**，所以超长输入可能悄悄丢掉末尾消息或候选，属于语义错误。本轮采用 2048 窗口、256 选项头，并在分词后验证完整输入长度；超限必须拒绝/弃权，由上游提供经明示的摘要或另一个有容量的实现处理，不能静默截断。实际运行建议先限定四位成员与一轮最多八次接续；六位候选仅测过 token 容量，未证明选择准确率。当前 Agent 不生成摘要，本轮也不假装它已经存在。

Mac MPS 上对早期紧凑投影（较短的选项说明）测过单道 move 热启动各 20 次：1024 截断输入中位 110.5 ms，1536 截断输入 182.3 ms，2048 完整输入（当时实际 1584 tokens）215.3 ms、p95 235.1 ms。上述表格已改按实际 v3 选项说明重算 tokens；新投影 1756 tokens 的延迟需在训练空闲后复测，不能沿用 1584 tokens 的时间。所有这些数值只涉及本机前向推理，不代表部署主机、网络或角色回复延迟。脚本和原始分词结果在 `context_probe.py`、`context_probe.json`。

## 数据设计与分组

- 训练 80 个独立对话家族、145 个原始决策步骤；4 次独立姓名/候选顺序置换，共 580 条记录。30 个家族来自此前 v2 的**训练来源**；剔除两个允许动作为空、与 SDK 契约不符的家族；另有 50 个全新原创家族。没把 v2 comparison 或封存集加入训练。
- 新验证 13 家族 19 步 ×3=57 条；校准 12 家族 19 步 ×3=57 条；新 comparison 20 家族 30 步 ×3=90 条；封存 holdout 8 家族 13 步 ×3=39 条。整段对话及反事实姐妹分支在同一分组。comparison SHA256 `1ddb672acd1322c4ff46a3b74048be842484efbeb7fce38caa4b2eb6cc191053eea11fe2e77f6401074a60c`；holdout SHA256 `f4d824b9378d5747712c6545f9b3b76d40d01b0b1161ffe2cc191053eea92416`。在首次 comparison 评估前冻结。
- 训练动作：respond 364、clarify 52、wait 76、finish 88；新 comparison 分别 54、9、12、15。训练中 12 个家族被加上较长的已公开旧话题上下文，产生 108 条记录；comparison 有 3 个这类家族、18 条记录。它们仍是同一原始家族的变体，不能算作新的独立对话。
- 真实 `DecisionRequest` 的允许动作至少一项，本轮全部满足；无候选 ID 越界，点名重名样本要求澄清。`abstain` 仍是安全出口选项，但**没有足够可审查的语义弃权正例**，本轮不测其召回，也不得用其置信度作自动执行保证。模型状态将 pinned user_request 与最新 trigger 各保留一次，其他已公开文本保持时序及稳定作者 ID；不会把未播完的生成当公开事实。
- 数据是原创编写的合成文本，作者对唯一下一步的判断可能有主观性。后续应另做人工复核与真实键入文本影子评估。当前既没有这种金标，也不声称本数据代表所有自由对话。

`audit.py` 在训练前检查家族隔离、SDK 动作约束、每条金标、反事实同候选映射、选项完整与实际 tokens。当前五组均通过；训练最大 1598 tokens，新 comparison 最大 1599 tokens，均小于 2048。详见 `data-audit.json`。

## 配方和预定检查

从未改动的 r14 checkpoint 初始化独立研究 run `ip-ensemble-v3`，MPS 训练 8 轮，最后 8 层解冻，encoder LR 5e-5、head LR 2e-4，2048/256 窗口，按 val NLL 选择最佳轮。温度仅从 calib 拟合。旧 r14 发布权重与 IP v1/v2 实验均不覆盖。

**训练前资源修订（仍未评估 comparison）：** 初次 batch 8 在第一轮结束时验证准确率 16/57、NLL 1.5518；保存 1.2 GB checkpoint 时因 macOS 交换空间增长而报 `No space left on device`，未留下有效 checkpoint，磁盘余量约 5.8 GB。原始样本和评估集未改动。为降低峰值内存，将 microbatch 改为 4、梯度累积 2，保持有效 batch 8 与学习率/轮数不变；重跑写到独立 `ip-ensemble-v3-b4`，以下所有正式指标仅来自重跑。若仍无法安全保存则停止，不清理既有有效实验产物来挤空间。

先只看 train 和 val：若训练 move 准确率低于 **85%**，或 val move 低于 **65%**，或 val 中应 wait/finish 的 15 条出现超过 **1 条错误发言**，新 comparison 继续封存，不因训练失败而消费它。可在后续独立版本中根据 train/val 重新审查配方，但要记录版本和变更。若通过开发门槛，才一次评估冻结的新 comparison，并与 r14 和旧 IP-only **同题 move 指标**比较。进入文本影子集成的研究门槛：comparison move 至少 **80%**、需要静默的 wait/finish **零误发言**、点名及澄清各至少 **80%**，并逐家族/上下文长度报告。仍需真正用户键入文本和具体 instruction 的独立验证后才可考虑自动调度。holdout 在本轮模型选型前不评估。

## 结果（训练后填写）

正式重跑 `ip-ensemble-v3-b4` 在 Mac MPS 完成 8 轮，耗时 780.7 秒（约 13 分钟）；按预定 val NLL 选第 2 轮 checkpoint，NLL 1.4016、当轮准确率 26/57。checkpoint 的 `model.safetensors` 为约 1.2 GB，SHA256 `dcdd9096a7b9baf5f8bc772eaccb4548d0ed487e076789d0e5f9c931c0318a78`。训练后 5.6 GiB 磁盘可用空间。第 7 轮曾达 34/57，但 NLL 升至 4.0374；按预先登记的规则没有改用它。完整逐轮数据在 `../../runs/ip-ensemble-v3-b4/checkpoint/train_summary.json`。

| 开发指标（第 2 轮 checkpoint） | 训练 | 验证 | 登记门槛 |
|---|---:|---:|---:|
| 完整 move 正确 | 374/580 = 64.5% | 26/57 = 45.6% | 训练 ≥85%，验证 ≥65% |
| 只看动作种类 | 513/580 = 88.4% | 35/57 = 61.4% | 诊断项，无单独门槛 |
| 需要成员时，成员 ID 正确 | 229/416 = 55.0% | 19/42 = 45.2% | 诊断项，无单独门槛 |
| 应 wait/finish 却选择发言 | 11/164 | 4/15 | 验证 ≤1 |
| 长公开历史 | 45/108 = 41.7% | 5/12 = 41.7% | 诊断项 |
| 短公开历史 | 329/472 = 69.7% | 21/45 = 46.7% | 诊断项 |
| 双候选 / 三候选 | 102/128、258/416 | 22/33、4/24 | 诊断项 |
| 反事实两分支同时正确 | 0/8 | 0/3 | 诊断项 |

验证集只有 13 个独立家族；同一家族的置换不是独立样本。长短上下文和候选数也来自不同家族，以上差异不能单独归因于长度或候选数。逐题记录及分层摘要在 `../../runs/ip-ensemble-v3-b4/eval/`。三个预登记开发门槛均**失败**。尤其动作类别与目标成员不能稳定同时选对，错误并非只由窗口截断造成：五组数据经审计均未发生选项或状态截断。验证中 4/15 条应安静的请求误选发言，不能自动执行。

训练来源复核：沿用 v2 训练家族的 252 条中正确 168 条；新写 v3 家族的 328 条中正确 206 条。两个来源都没有被稳定拟合。145 个原始训练步骤中，只有 61 个在所有四种姓名/候选置换下都正确，19 个在四种置换下都错误。这支持优先排查成员绑定与表示方式，不能把 580 条变体误当成 580 个独立场景。

为拆开长度和场景，门槛失败后又在**同一验证记录**做了额外开发诊断：仅对两个有旧话题背景的家族、12 条置换记录，移除前 11 条与当前目标无关的旧公开发言，金标、候选、当前请求与后续真正接话均保持不变。输入长度从 1169–1241 降为 326–398 tokens；原样和移除背景各正确 5/12，逐条 4 条两者均对、1 条仅长版对、1 条仅短版对、6 条两者均错。故目前**没有证据证明这 11 条旧背景本身降低了这两个家族的准确率**；样本仅两个独立家族，也不能证明长上下文普遍无害。脚本及报告在 `paired_context_eval.py` 和 `../../runs/ip-ensemble-v3-b4/paired-context/`。这项事后开发诊断没有接触 comparison/holdout。

依照登记流程，**未在新 comparison、holdout 或 calib 上推理**。未做温度校准，因为当前 checkpoint 没有通过进入后续评估的开发门槛；它们保留给以后预先记录的新假设。旧 v2 comparison 已用于历史选型，也没有拿来反复调这个版本。r14 的 release checkpoint 未更改，v3 仅是独立研究产物；不能据此宣称比 r14 的 Ensemble 调度更好。

同一台 Mac MPS 上按实际 v3 选项文本、完整输入和每种 20 次热启动前向测得：

| 压力样本 | 实际输入 tokens | 中位延迟 | p95 延迟 |
|---|---:|---:|---:|
| 短请求 | 512 | 46.8 ms | 47.9 ms |
| 普通接话 | 941 | 97.1 ms | 102.5 ms |
| 四成员、默认回复预算压力 | 1756 | 213.4 ms | 228.2 ms |
| 六成员压力 | 1946 | 245.0 ms | 252.1 ms |

测量原始值见 `latency_probe.json`。长讨论 2875 tokens、线协议上限 64 条消息 9479 tokens 都不能在本轮 2048 窗口内完整输入。数字是合成长度压力和本机单道前向耗时，不是用户文本分布，也不包括网络、摘要、角色生成和编排耗时。当前可支持的结论仅是：text-only、四成员九条约 1756 tokens 的输入可以完整编码并在本机约 213 ms 中位完成一次选择；**选择质量未过门槛**。

## 下一步假设

先检查候选 ID 与名称在文本状态、选项和金标之间的绑定及反事实一致性，再以开发集设计一个受控的成员定位改进；不能靠再堆同模板的姓名置换声称增加了独立数据。补充来自用户键入、经同意脱敏的短文本对话时，按整段对话分组，人工复核每步的下一位、等待和收束，覆盖点名、同名、同一人续说、接力、插话改目标、澄清、静默及长历史。若无此类真实材料，可继续明确标注为合成的针对性诊断，但不得将其用作自动执行安全验收。上下文策略先用完整输入上限和显式拒绝超限；摘要及更长窗口要另行做保留指代和新目标的受控对照。

2026-09-28 补充：后续合成场景草稿改由 `generate_glm.py` 读取 `generation-plan.yaml`，调用用户配置的 GLM-5.3-Flash API，具体使用与审稿流程见 `GLM-DATA-GENERATION.md`。用户配置的密钥在智谱通用端点取得了真实响应；最初 v1 的三次有效 HTTP 请求未通过结构校验，因此没有候选进入训练。v2 改为让模型只生成扁平的场景素材，决策步骤由本地切片模板构造，再经语义审稿。旧实验的冻结评估集不变。
