# 家居续接：任务契约与标注规范（c 系列）

训练、开发、测试数据都按这份规范标。写数据前必读；规则没覆盖的情况，先在 §6 补裁决，再写数据。
2026-09-29 实验用的 `next` 题（`scenario.yaml`、`generators/continuation.py`、`eval/locked.jsonl`）是历史证据，不按本规范。

## 1. 什么时候问 Laya（Agent 侧前置条件）

Laya 只回答 Agent 已经建好有限选项的续接题，其余一律照旧交给 LLM。Agent 只在下面两种上下文里调用，而且 `HomeContext` 未过期（30 秒）、版本一致：

| 上下文 | 来源（`HomeContext`） | 题目 |
|---|---|---|
| **待选设备** | `pending=True`，proposal 是 `target_status="ambiguous"` 的控制提案：一个结构化动作 + 2–8 台都能执行它的设备，Agent 已经问过“A、B，要哪一个？” | `pick` |
| **刚操作过的设备** | `pending=False`，proposal 是已成功执行（有回执）的控制提案，或已回答的查询；目标 1–3 台，不含门锁、传感器、场景 | `follow` |

**不调用**：没有上下文、上下文过期、LLM 发出的开放澄清（没有结构化动作或候选不足两台）、焦点设备已不在目录里（失效焦点由 Agent 判断，Laya 看不到）、焦点含门锁。
可执行选项为空的题（例如 2026-09-29 实验里的“无焦点”）不存在：那时 Laya 没有可选的东西，只会把请求吞成“取消”。

## 2. 题目与状态（state_format `continuation-laya-v1`）

两道题都是 `choice`。选项名就是 Agent 能直接映射的东西，Laya 不产生新设备、新动作或数值。

### `pick`：待选设备

- 选项：每台候选设备一个（选项名 = 设备名；重名时按 Agent `device_options` 的规则写成 `主灯（客厅）`；说明 = `房间·类型`，类型用 SDK 的中文名：灯、空调、窗帘……），然后是两个出口：
  - `取消`：用户明确不要执行这次待确认的操作，也没有提出别的要求。
  - `重新理解`：改了动作或数值、要多台或候选之外的设备、没说清是哪台、提问、闲聊或提出新要求。
- 状态：
  ```json
  {"utterance": "就儿童房那个吧",
   "context": {"上一句": "把灯打开", "Agent": "儿童房灯、玄关灯，要哪一个？", "待执行": "打开"}}
  ```
  `待执行` 是 proposal 动作的中文短语：打开 / 关闭 / 调亮 / 调暗 / 调到50% / 设为26°C / 调高温度 / 启动 / 暂停……（`frames.py` 的 `action_phrase`）。
  `Agent` 就是 Agent 问出去的那句话（`choose_one`），候选的先后顺序以这句为准。

### `follow`：刚操作过的设备

- 选项：焦点设备都支持的动作，用单句任务 `action` 题的原名和原说明（不含 `上锁`）：

  | 选项 | 说明 | 适用（SDK 类型） |
  |---|---|---|
  | 打开或启动 | 开启、启动、开始运行 | 除传感器 / 门锁外全部 |
  | 关闭或停止 | 关掉、停止、断电、收起 | 同上 |
  | 调高或增大 | 调亮、升温、调大音量或档位 | 灯、空调、热水器、影音 |
  | 调低或减小 | 调暗、降温、调小、降下 | 同上 |
  | 设为指定的数值或模式 | 设到具体的温度、档位、百分比或模式 | 灯、空调、热水器、窗帘、风扇类、影音 |
  | 暂停 | 暂时停下，之后再继续 | 家电（扫地机、洗衣机……） |

  焦点有多台时取交集。最后一个出口 `重新理解`：换了或增加设备、只针对其中一部分、撤销刚才的操作、保持不动、提问、闲聊或其他新要求。**`follow` 没有 `取消`**（见 §4）。
- 状态：
  ```json
  {"utterance": "再调暗一点",
   "context": {"上一句": "把客厅主灯打开", "Agent": "已打开客厅主灯", "设备": ["客厅主灯"]}}
  ```
  `Agent` 是 Agent 回给用户的那句话（执行用 `done_phrase` 的写法，查询用状态描述，如“客厅空调开着，制冷 26°C”）。
- 数值由 Agent 的 lexicon 从原话里取（与单句任务相同）；Laya 选了 `设为指定的数值或模式` 而原话取不出数值时，Agent 交给 LLM。

## 3. `pick` 判定细则

只看 `utterance` 是否**明确**指向一台候选、并且**不改变**待执行的动作。

| 情况 | 金标 | 例（待执行“打开”，候选 儿童房灯、玄关灯） |
|---|---|---|
| 用房间、设备名、类型或别名指出一台 | 那一台 | “儿童房的”“玄关那盏”“就玄关吧” |
| 用顺序指出一台（以 `Agent` 那句的顺序为准） | 那一台 | “第一个”“后面那个” |
| 选一台 + 附和词 / 重复同一个动作 | 那一台 | “嗯，玄关的”“打开儿童房的吧” |
| 否定一台 + 明确肯定另一台，动作不变 | 被肯定的那台 | “不是儿童房，玄关的” |
| 句内改口，最后落在一台上 | 最后那台 | “儿童房……不对，玄关” |
| 同名设备：有区分线索（房间、位置） | 对应那台 | 候选 `主灯（客厅）`、`主灯（主卧）`：“客厅那个” |
| 只否定、没有肯定哪一台 | 重新理解 | “不是儿童房的”（即使只剩一台，也不替用户补） |
| 选一台但改了动作或数值 | 重新理解 | “玄关的关掉”“儿童房的调暗点” |
| 两台都要 / 全部 | 重新理解 | “两个都开”“都要” |
| 候选之外的设备或房间 | 重新理解 | “是窗帘”“卧室的”（卧室不在候选里） |
| 没说清是哪台：附和、委托、随意 | 重新理解 | “好的”“嗯”“随便”“你看着办”“哪个都行” |
| 同名设备没有区分线索 | 重新理解 | 候选两个“主灯”：“主灯” |
| 明确不要这次操作，且没有别的要求 | 取消 | “算了”“不用了”“两个都不要”“先不开了”“我自己去开” |
| 取消 + 新要求 | 重新理解 | “不开了，帮我把空调打开”“算了，放首歌吧” |
| 暂缓 | 重新理解 | “等一下”“我想想” |
| 提问（关于候选或别的） | 重新理解 | “哪个是儿童房的？”“玄关灯现在开着吗？” |
| 闲聊、无关 | 重新理解 | “今天好累”“讲个故事” |

## 4. `follow` 判定细则

只看 `utterance` 是否是对**全部焦点设备**的一个明确操作，且这个操作在选项里。

| 情况 | 金标 | 例（焦点 客厅主灯，刚“已打开客厅主灯”） |
|---|---|---|
| 代词 / 省略宾语 + 明确动作 | 那个动作 | “关了吧”“把它关掉”“再亮一点”“调到50%” |
| 点名焦点设备本身 + 动作 | 那个动作 | “客厅主灯关一下” |
| 重复刚才的动作 | 那个动作 | “再开一下”（照字面，不替用户推断） |
| 程度词（亮 / 暗 / 高 / 低 / 大声 / 小声） | 调高或增大 / 调低或减小 | “太亮了调暗点”“再高两度” |
| 具体数值或模式 | 设为指定的数值或模式 | “开到一半”“调成制冷”“设26度” |
| 动作不在选项里（设备做不到） | 重新理解 | 焦点是开关：“调亮一点” |
| 换设备 / 加设备 | 重新理解 | “卧室的也关了”“那主卧的呢” |
| 焦点多台，只针对其中一部分 | 重新理解 | 焦点 客厅主灯、灯带：“只关灯带” |
| 撤销 / 取消刚才的操作 | 重新理解 | “取消”“撤回”“刚才那个不算”——已提交的操作由 Agent 依据回执处理，Laya 不宣称撤销 |
| 保持不动 | 重新理解 | “别动它”“就这样吧” |
| 只抱怨、没说动作（隐含意图） | 重新理解 | “太亮了”“有点冷”（c 系列先保守，见 §6） |
| 提问 | 重新理解 | “现在几度？”“开着吗？” |
| 感谢、确认、闲聊、新领域 | 重新理解 | “好的谢谢”“放首歌” |

## 5. 数据卫生

- **金标来自剧本**：`frames.py` 先定上下文和意图（家族），金标由本规范推出；写手只写 `utterance`，不改金标。写不出自然的话就标 `skip`，不要硬写。
- 话语里不要出现替模型判断的元信息（“我选第一个选项”“请取消待确认操作”）。口语、零碎、带语气词都可以。
- 每批抽 10% 由另一位标注者盲标（只看状态和选项，不看家族）；不一致的逐条裁决：文字没支撑金标 → 重写或丢弃，规范没覆盖 → 补 §6。
- 开发 / 测试集的户型、写手调用与训练分开；**不得抄评测集的句子**，assemble 也按状态哈希拦截。
- 来源分开登记（`source`）：`claude-writer`、将来的 `replay-authorized`（真实授权回放，纠错标签按本规范人工裁决，不用模型自己的输出）。

## 6. 裁决记录

- **C1（2026-09-29）**：`follow` 不提供“取消”。执行后说“取消 / 撤回”通常是要撤销已执行的动作，交给 LLM 与 Agent 回执处理；“别动它”价值低，也交给 LLM。
- **C2（2026-09-29）**：隐含意图（“太亮了”“有点冷”）在 `follow` 里先标重新理解。单句任务里它是控制，但续接接管要求话语明确支持动作；以后有回放证据再放开。
- **C3（2026-09-29）**：两台候选时“不是 A”也标重新理解，不替用户推出 B。Laya 只执行明确支持的选择。
- **C4（2026-09-29）**：“两个都要 / 全部”标重新理解。多选以后可以作为新选项加进 `pick`，c 系列不做。
- **C5（2026-09-29）**：`pick` 里“另一个 / 剩下那个 / 别的那个”在没有先行指代时标重新理解（Agent 只问了“A、B，要哪一个？”，“另一个”没有参照）。
- **C6（2026-09-29，dev 盲标提出）**：程度词带幅度（“再高两度”“降百分之十”“调亮10%”）是相对调节 → 调高或增大 / 调低或减小；
  只有说出目标值（“调到26度”“开到一半”“设成制冷”）才是设为指定的数值或模式。
- **C7（2026-09-29，dev 盲标提出）**：焦点设备不支持调高 / 调低时，程度词（“开大点”“再拉开一点”）标重新理解，不改判成设为指定的数值。
- **C8（2026-09-29，dev 盲标提出）**：`follow` 里“恢复原样 / 退回去 / 还原”与“取消 / 撤回”同义，是撤销已执行的操作 → 重新理解；
  查询后的“就这样 / 关着就行”是保持现状 → 重新理解。只有明确说出动作（“关掉吧”“再打开”）才选动作。
- **C9（2026-09-29，dev 盲标提出）**：`pick` 里用名字的一部分、别名或类型（“夜灯”“柜式的”）指设备，只要在候选里**唯一**对应一台，就选那一台；
  对应两台以上 → 重新理解。
- **C10（2026-09-29，dev / test 盲标分歧）**：`pick` 的选择依据必须在状态里看得见（选项名、`房间·类型` 说明、Agent 那句话）。
  Agent 的候选不带产品类型：说“吸顶灯那台”“柜式的”而名字里没有这个词 → 重新理解。`build.py` 对“按特征选”（P02）自动检查并改标，
  训练池里其他按名字 / 房间选中、但话和金标设备的名字 / 房间一个二字片段都对不上的，丢弃。
- **C11（2026-09-29，test 盲标分歧）**：“暂停”只在说出“暂停”或明确“待会儿再继续”时选；“停下 / 停掉 / 停一下 / 先停下”都是关闭或停止。
  设备没有暂停选项时说“暂停” → 动作不在选项里 → 重新理解。
- **C12（2026-09-29，盲标提出）**：设备状态与动作字面矛盾（灯刚关说“调亮一点”、空调开着说“打开”）时照字面选动作，不替用户推断；
  执行与否由 Agent / Hub 按当前状态处理。
- **C13（2026-09-29，盲标提出）**：“拉满 / 开到最大 / 最亮”是目标值（100%）→ 设为指定的数值或模式；Agent 取不出数值时交给 LLM。
