# 参与决策（陪伴 + IP 角色团）：laya 路线计划

2026-09-28 起。本文件是这条路线的唯一计划与登记处；每个 release 的结果写进同目录 `EXPERIMENTS.md`。

## 1. 目标

对应产品契约 `eidolon_sdk.biz.participation`（schema v2，`ip_team.participation`）：给定原始用户请求、已播完的公开历史、
最新触发、候选角色（稳定 ID + 名字 + 角色说明）、允许动作和剩余预算，**只做决策**：

| SDK 结果 | 含义 |
|---|---|
| respond + 1 位候选 | 这位角色接着发言（可以是同一位继续，不轮换） |
| clarify + 1 位候选 + 有界任务 | 这位角色问一个澄清问题，然后等用户 |
| wait | 不说话，等用户 |
| finish | 本轮请求已完成或用户明确结束（不关闭场次） |
| abstained | 无法可靠决策，不带 proposal |

陪伴（单聊）按同一契约处理：候选只有 1 位。回复文本由其他大模型生成。部署目标是云端 GPU，按质量选型。

## 2. 为什么沿 laya，以及之前为什么不行

之前 laya（ip-team v6–v8）和 JevK5 的失败有共同根因，和智能家居 r13 之前一样（见仓库 `laya/train/EXPERIMENTS.md`）：

1. **数据少两个数量级**：150 个快照 / 25–81 个家族（家居 r14 用 15,374 条）；陪伴 12 个快照，澄清 0，弃权 1。
2. **可训练容量太小、连训练集都学不会**：laya v8 只训最后 8 层（训练集 93/150）；JevK5 只在最后一个注意力块做 LoRA（16.8 万参数，
   训练集弃权 0/5）。家居 r13 → r14 只把 8 层换成全部 22 层，测试集 89.4 → 96.8%。
3. **五种决策压成一道题**，还把"无法可靠决策"（模型自己的不确定）当成一个类别训练——v8 弃权占 1/3，训完后该回应的 17/24 不回应。
4. **读字母概率的小 LLM 有位置偏差**（逆序 19 → 14–15/24）；laya 每 epoch 打乱选项、选项有独立 marker。
5. **评测只有 24–76 条**，选择在噪声里；v8 的生成数据还能用句长猜对一半动作（表面偏差）。

laya 的现成优势：一次请求多道类型化题 + `ask_if` 依赖（家居的意图 / 设备 / 动作）、每题校准、全流程（生成 → 组装 → 训练 → 校准 →
评测 → 打包）、门槛与停止规则、NPU / ONNX / 服务端都已跑通；全量解冻 1.5 万条约 2.5 小时。
**要实测的风险**：322M 的编码器能不能读懂多轮历史（上限测试 + 学习曲线回答）。

## 3. 题目设计（模型只回答语义问题，SDK 结果由运行时映射）

| 题 | 类型 | 选项 | 何时问 |
|---|---|---|---|
| `action` | choice | respond / clarify / wait / finish（**永远给全 4 个**，不按 allowed_actions 删） | 每次 |
| `speaker` | choice | 候选 M0…Mn（名字 + 角色说明），可多个都对 | `action ∈ {respond, clarify}` |
| `clarify_about` | choice | 指代不明（不确定指哪位 / 哪个）/ 要求不明（不确定要做什么）/ 对象不在场（点名的角色不在候选里） | `action = clarify` |

**abstain 不是训练类别**，由运行时决定：
- `action` 的最高项不在 `allowed_actions` 里 → abstained（例如该澄清但不允许澄清）；
- `action` 或 `speaker` 的校准后置信度低于门槛 → abstained（门槛在开发集上按"不确定就交给 agent"的策略选，同家居 r14）；
- clarify 的 instruction 由 `clarify_about` 映射到固定的有界任务说明（"请问清楚用户说的是哪一位"等），不由模型生成台词。

## 4. 状态（laya `state`）

```json
{"场景目标": "...", "候选": [{"编号": "M0", "名字": "阿舟", "角色": "..."}],
 "本轮用户请求": "...", "公开记录": [{"说话": "用户|M1 阿舟", "内容": "..."}], "最新一条": "M1 阿舟：……", "剩余回复次数": 5}
```
- 编号 M0…Mn **每条样本随机映射**（训练时打乱，评测时固定一种再测换序）；显示名可重复（同名角色）。
- 公开记录保留最近若干条、固定带上本轮用户请求；首版上限按 token 实测定（目标 max_len 2048）。

## 5. 数据

**标注规范**：`LABELING.md`（本目录）。写数据前先定规则，有争议先补规则。

**生成方式：剧本式多轮 episode**（标签来自剧本，文字由模型写）：
1. Python 按家族模板生成剧本：场景（1–5 位候选，名字 / 角色池，含同名）、用户请求意图、每一步的决策序列
   （例：点名阿舟说两次 → respond 阿舟 → respond 阿舟 → finish）。
2. 写手（GLM 脚本 / Claude 子代理）按剧本写自然的用户话和角色发言，不改决策；每一步形成一个快照，金标 = 剧本。
3. 盲审：另一个写手只看公开状态独立标 10%；和剧本不一致的样本说明文字没有支撑标签，重写或丢弃。

**家族**（每个家族都要有"同框架但决策不同"的对照）：
- 团队：点名一人说一次 / 说多次 / 点名两人依次 / 开放问题（多人都可）/ 交棒回应实际观点 / 同一人补充 / 追问某人 /
  按角色专长选人 / 指代澄清与恢复 / 点名不在场 / 同名有区分线索 vs 无线索 / 要求安静与恢复 / 明确结束与新请求 /
  澄清发出后等待 / 中途改要求 / 预算快用完。
- 陪伴：闲聊与继续 / 安静陪伴（可简短回应）vs 明确别说话 / 暂停与恢复 / 结束与新请求 / 需求不明澄清与恢复 /
  多段请求未完成（讲三个笑话）/ 角色说完后判断完成。

**规模与比例（p1）**：约 1,500 个 episode、5,000 个快照；陪伴 ≥ 40%；动作分布贴近真实使用（respond 为主，
wait / finish / clarify 各占一定比例），不按类别平均（家居 r13 的教训）。

**来源分开**：GLM 与 Claude 写手各占一部分；**开发 / 测试集的写手来源与训练分开统计**，并保留至少一套来源不进训练的评测，检验文风过拟合。

## 6. 评测

| 集合 | 规模 | 来源 | 用途 |
|---|---|---|---|
| p-dev | ≥ 400 快照 / ≥ 120 episode | 独立写手，家族与训练不重叠 | 误差分析、选门槛、release 门槛 |
| p-test | ≥ 400 快照 | 另一批独立写手 | 只看汇总，只在候选上跑 |
| 24 条筛查（`evals/participation/product-readiness-v1`） | 24 | 既有 | 冒烟，永不进训练 |
| 回放 | 若干场完整对话 | 决策模型 + 真实回复大模型 | 查循环、完成即停、澄清恢复 |

评测集全量双标；双标意图一致率 < 90% 说明规范有歧义，先改规范。

**指标**：动作准确率与混淆（尤其"应停却发言"= 金标 wait/finish 而预测 respond/clarify）、人选准确率（respond/clarify 时）、
端到端（动作与人选都对）、换序 / 改名一致性、整 episode 全对率、按"不确定就交给 agent"策略的直接执行精度与覆盖。

**上限测试**：用 GLM 按 `LABELING.md` 零样本回答 p-dev（约 80–150 次调用，每次 5 个快照）。大模型能到 90% 以上 → 任务定义清楚、可当老师；
大模型也做不好 → 先修规范。

## 7. Release 计划与停止规则

- **p1**：家居 r14 配方（全部 22 层解冻、3 epoch、val NLL 选轮、按题拟温度），数据约 5,000 快照。
- **p2 起**：每轮一个改动（按 p-dev 误差分析定：数据概念 / 历史长度 / 配方），先登记后训练。
- **停止规则**：
  1. 成功：p-dev 上动作 ≥ 92%、端到端 ≥ 88%、应停却发言 ≤ 3%、换序一致 ≥ 95%，且门槛通过 → 候选，跑 p-test 与回放。
  2. 平台期：连续两轮 p-dev 主要指标都没超出噪声 → 停止只加数据，换配方或基座对照。
  3. 训练集探针学不会 → 容量 / 表示问题，不再加数据；学会但 p-dev 不行 → 泛化问题。
  4. 预算：最多 p5；每轮的 GLM 调用数在登记时写明。

## 8. 工程约束

- 同一个工作目录里 codex 有未提交的框架修改（`assemble.py` / `evaluate.py` / `train.py` / `cli.py` / `generators.py` 等，
  r17–r18 的切分与评测修正）：本路线新代码放新文件，不改、不提交这些文件；需要改框架时先和用户确认。
- MPS 同一时间只跑一个训练；开训前确认没有别的训练在跑。
- 外发给 GLM 的只有规范和虚构合成文本；密钥只从环境 / 指定文件读，不写进仓库；调用账本落盘，失败也计数。
- 不读 v7 / v8 等封存测试；24 条筛查、p-dev、p-test 永不进训练；每批数据跑近似重复清理。
