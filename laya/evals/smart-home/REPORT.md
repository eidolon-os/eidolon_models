# laya 智能家居控制决策评测报告

生成：2026-09-25｜模型：laya-multilingual（zero-shot，未微调）@1c5edc17｜机器：Apple M3 Pro｜用例：182 条，9 个场景

## 结论

**一句话：zero-shot 的 laya 已经很会“认设备”，但还不会“判断是不是命令”，也不会用“多个设备 / 家里没有”这两个出口；
控制命令端到端只有 41%（规则基线 60%），不能直接拿来执行命令，必须微调。性能不是问题：Mac GPU 上每条 71–82 ms。**

1. **是不是控制命令**：说“是控制”时基本是对的（精确率 95%），但漏掉三分之一（召回率 67%）。三分类意图 66%，
   低于规则基线的 76%。最大的错是 **把控制判成“无关”（46 次）**：隐含意图几乎全错（“好热啊”“客厅太暗了”，10%），
   “洗衣机开始洗衣服”“电饭煲开始煮饭”这类明确指令也会判成无关；**状态查询只认出 40%**，多数被判成无关。
2. **控制哪台设备（强项）**：明确指令 98%、状态查询 100%、**语音识别错字 85%（规则基线 35%）**、
   同类设备分房间 69%（基线 44%）、38 个选项的大户型仍有 90%。语义理解明显强于关键词匹配。
3. **两个出口完全不会用**：多设备 / 场景 0%，家里没有该设备 0%——而且是**高置信地选错**：
   “打开电视”（家里没电视）→ 门铃 0.87，“空调调到 25 度”（家里没空调）→ 地暖 0.98，“车库门关上” → 智能门锁 0.97。
   对执行型控制，这是最危险的一类错误。另一个系统性混淆是**卧室里的灯与空调**（“关一下主卧的灯”→ 主卧空调）。
4. **动作 76%**：“拉上窗帘”判成调高、“开到最大档”判成打开这类细粒度错误。
5. **置信度还不能当安全闸**：设备最高概率 ≥ 0.9 时覆盖 70%、准确 88%；意图 ≥ 0.9 只覆盖 18%。
   出厂未校准，且第 3 条里的错误置信度都很高。
6. **性能（Mac M3 Pro，一次请求 3 道题、约 478 token）**：torch + MPS **p50 71–82 ms / p95 88–91 ms**（两次运行，机器负载不同）；
   torch CPU 221 ms；ONNX CPU 447–465 ms（ORT 限 6 线程只快 4%）；常驻内存 1.0–2.1 GB。
   四种运行 182 条的选择**完全一致**，后端可按部署环境随意切换。选项从 20 增到 38，延迟只多约 5 ms。

**建议**

- **微调的数据按本次失败切片来造**：隐含意图、状态查询、“开始 / 回去充电”类动词、多设备与场景、家里没有、
  卧室灯 vs 空调、动作细分。评测集直接复用 `scenarios/`（它不进训练集）。
- **上线形态**：laya 负责“哪台设备”（它最强的一环），意图与两个出口先用规则或升级给 LLM；
  **门锁、车库门、安防等敏感设备无论置信度多高都要二次确认**；温度校准后再用概率做门控。
- 与社区微调模型（MacJev、laya-cn-a）的对比见 [COMPARISON.md](COMPARISON.md)。
- 本次用例 182 条，由单人手写，覆盖面广但措辞风格单一；隐含意图与场景的金标取决于产品策略（有的产品会先确认再执行）。
  这是 zero-shot 基线，不代表微调后的上限。

## 测试设置

- 每条用例一次请求、三道题：**意图**（控制 / 查询 / 无关）、**设备**（该户设备清单 + “多个设备或整屋” + “没有对应的设备”）、**动作**（打开 / 关闭 / 调高 / 调低 / 设定 / 暂停 / 上锁）。
- 户型：`apartment`、`house` 各 18 台设备（加两个特殊项共 20 个选项），合起来覆盖 15 类；`villa` 为两者合并（38 个选项）。见 `homes/`、`taxonomy.md`。
- 金标允许多个可接受答案（如“好热啊”开哪台空调都算对）。设备只对查询/控制用例计分，动作只对给了动作金标的用例计分；**端到端** = 控制用例的意图、设备、动作全部正确。
- 对照组：通用关键词规则基线（设备类型词表 + 房间词 + 动词/疑问词，`run_eval.py` 中 `rule_baseline`）。

## 设备清单变长（20 个选项 → 38 个选项）

同一批 20 条语句，分别放在 20 个选项（原户型）和 38 个选项（villa）下：

| 选项数 | 意图 | 设备 | 端到端 | 客户端 p50（mac-torch-mps） |
|---|---|---|---|---|
| 20 | 85% | 95% | 70% | 81.6 ms |
| 38 | 85% | 90% | 65% | 85.9 ms |

头部预算固定 256 token，选项越多每个选项分到的 token 越少（38 项时约 6 个），所以序列长度几乎不变、延迟只略增；准确率风险来自选项描述被截短。
