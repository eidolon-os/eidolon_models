# c10 运行效率实验（2026-10-09）

## 范围

固定 c10 `e8254243`、FP16、完整问题文本、历史上下文、阈值和决策策略。没有训练、量化或绕过 Laya，没有改动生产服务/配置，没有调用 LLM 或设备执行接口。

独立进程使用板上生产版本的 Python/Models 运行时和原制品；实验文件放在 `/tmp/laya-efficiency-20261009`。生产服务继续运行，实验间核对其 served 计数；这不是独立硬件，空闲生产进程仍驻留。NPU 核 1、2 用于实验，未占用 participation 的核 0。

输入复用 [326 条冻结输入](../c10-npu-20261009/requests.jsonl)：20 条连续对话、36 条独立输入、54 条上下文安全输入、216 条原验收输入。本次没有重建今晚 17 轮的原始模型请求，因为当时未开启上下文/推理记录，不能声称是逐字逐状态复现。

## 实验设计

1. **实测成本调度**：先逐核、逐档位预热 2 次、测量 5 次中位数；对最多 8 题穷举合法核分配，最小化估算的最慢核完成时间。只改排程，不改 bucket、模型或输入。每核仍按短题优先。
2. **160 档**：原 128/256/384/512 档间增加 160 档，只有 129–160 token 的问题改用它。20 条对话的 action 都在该范围。保留原调度算法，单独观察减少 padding 的作用。

两个方案分别做 20 条对话 × 3 次重复 × A/B 两种模式，共各 120 次推理。逐案例交替 AB/BA 顺序，避免总先测基线带来的漂移。160 档另外进行完整 326 条输入 A/B 对照。

160 档实验在同一进程中加载五种档位，通过可用 bucket 列表切换基线/候选，保证权重、温度环境和其余实现一致。基线也驻留额外档位，因此此测量不比较生产内存占用。编译结束后才开始 160 档测试。早期调度实验尾段与 CPU 编译有时间重叠，整体约 1% 的收益不能视为稳定收益。

校准使用合成补齐序列，仅测硬件成本，不纳入准确性统计。性能统计不含加载、校准和预热。

## 对话重复测试结果

|方案（各 60 次/模式）|基线平均|候选平均|基线 P50 → 候选|基线 P95 → 候选|最大耗时变化|
|---|---:|---:|---|---|---|
|实测成本调度|716.3ms|707.2ms|732.9 → 726.0ms|769.0 → 772.8ms|960.6 → 824.9ms|
|增加 160 档|707.4ms|651.0ms|718.6 → 664.7ms|762.2 → 722.5ms|960.5 → 844.8ms|

160 档对话平均快 8.0%，P50 快 7.5%，P95 快 5.2%。按每条输入三次平均，20 条中 19 条更快，唯一变慢输入约增加 2.0ms；最慢长上下文输入平均从 957.9ms 降到 821.8ms（快 14.2%）。以上是 Engine.predict 耗时，包含构造输入、NPU、CPU scoring 和解码，不含 HTTP、ASR、LLM、Hub 与端侧播放。不能将其直接当作整条语音链路提速比例。

调度与 160 档分别比较了 288 对问题输出、60 对当前 Agent 接纳决定，分类选择和接纳决定均无变化。最大概率漂移分别为 0.0005 和 0.0036；因此不是逐 bit 完全一致。全部无截断。

## 全量回归结论

共完成 **892 次有效板端对照推理**（120 次调度 A/B + 120 次 160 档重复对话 A/B + 652 次全量 A/B，不含预热/校准）。全部完成，无输入截断；这些是引擎直接调用，未测 HTTP deadline 或并发拒绝率。

|全量分组|输入数（每种模式）|基线平均|160 档平均|平均下降|
|---|---:|---:|---:|---:|
|连续对话|20|717.5ms|670.6ms|6.5%|
|上下文安全|54|733.5ms|647.0ms|11.8%|
|独立口令|36|407.5ms|292.7ms|28.2%|
|原 target-accept|132|269.6ms|269.3ms|0.1%|
|原 target-accept-single|44|352.9ms|264.3ms|25.1%|
|原 controls-accept|40|267.1ms|246.0ms|7.9%|

全量混合集平均 400.1 → 355.5ms（下降 11.1%），P95 747.2 → 700.3ms，最大 939.1 → 820.3ms；两边都没有超过 1 秒。混合集含很多单题输入，**355.5ms 不是典型多轮对话延迟**。

326 条输入共有 778 个分类问题，218 个问题（161 条输入）落在新 160 档。全部 778 对分类选择一致；110 对当前 model-first 接纳/被接纳 proposal 一致，216 对旧验收策略结果一致。最大概率差 0.0114，数值并非完全相同。概率漂移必须在未来边界用例扩展时继续观察；本次不改变阈值来掩盖它。

三组实验期间生产 smart-home served 均保持 17 → 17；实验结束进程已退出，Agent、Laya、participation 均 active，生产仍是 c10 + 原 128/256/384/512 档。没有真实设备执行，也没有验证用户耳朵听到回复的端到端时延。

**建议：优先将 160 档进入发布候选，暂不采用实测穷举调度。** 前者对典型对话有两组约 6%–8% 的可重复收益，独立口令收益更大；后者整体收益不足，虽然改善长尾但引入调度复杂度。新增 160 档需要额外模型驻留（新权重图加共享副本），本次没有单独测增量 RSS/NPU 地址空间占用，因此正式上线前还需同时运行其他模型的资源、HTTP deadline/并发和长时间稳定性验收。

## 自动化检查

Engine、NPU 和实验调度器共 25 项自动化测试通过。实验调度测试覆盖 100 组确定性随机输入的任务不丢失、合法核放置和估计关键路径不劣于原排程，并单独验证长上下文排程。Ruff E9/F 和 git diff 检查通过。

## 制品与复跑

160 档从原 c10 权重导出，ONNX 12 个抽样最大 logit 差 4.48e-5。RKNN Toolkit 2.3.2 FP16 编译耗时约 75 秒，返回成功；编译日志包含 `Unkown op target: 0`，与既有导出日志同类，不能声称无告警。制品约 262 MB（250 MiB），只保留临时路径，哈希见 `artifact.json`，未写入生产模型目录，也未作为发布默认值。

```bash
# Mac: 新建输出目录，脚本不会覆盖原模型
laya/.venv/bin/python laya/evals/c10-efficiency-20261009/export160.py \
  --source laya/models/laya-smart-home/e8254243 --out /tmp/laya-c10-bucket160

# Board: 使用已安装 RKNN Toolkit 的 Python 转换输出目录
python laya/deploy/rk3588/laya_npu.py convert <isolated-onnx-directory>

# Board: 原制品调度对照；指定有权读取原制品的用户
OPENBLAS_NUM_THREADS=1 python bench.py --model <c10-model> \
  --requests requests.jsonl --out scheduling

# Board: 临时模型包含原档位和新 160 档；保留原 manifest/tokenizer/scorer
OPENBLAS_NUM_THREADS=1 python bench.py --model <isolated-model160> \
  --placement '1:128,160,256,384,512|2:128,160,256' \
  --requests requests.jsonl --out bucket160-full --bucket160 --all --rounds 1

# Mac: 通过 Agent 原策略自动比较接纳决定，不连接服务
../eidolon_agent/.venv/bin/python laya/evals/c10-efficiency-20261009/analyze.py <result-directory>
```

`responses.jsonl` 保留 A/B 输出，`analysis.json` 区分概率、分类和接纳决定差异。`summary.json` 的 differences 是完整答案字典差异（包括小数），不等同于分类错误。P95 使用排序后 `floor(.95*(n-1))` 位置，小样本统计不替代长期负载测量。

实验脚本不是生产调度配置：穷举上限为 8 题，服务最大可收 32 题；如产品化须增加有界算法与回退路径。当前只建议将可复现收益进入下一轮发布验收，不直接上线。
