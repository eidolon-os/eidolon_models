## 精度与接纳决定

326次全部HTTP200，0截断，778个问题答案覆盖128/256/384/512档，分别169/536/72/1题。

与Mac FP32有3个argmax差异：两条上下文否定口令的设备问题，以及一条“第二盏”的pick问题。三个都低于接纳阈值，没有改变最终接纳或兜底决定。冻结验收集最大概率差约0.0303。

- 110个固定新链路输入：**接纳决定及已接纳提案零差异**。
- 216个原冻结验收输入：按原0.8单句、0.95续接、0.5取消阈值计算，**决定零差异**。
- 动态新链路：20/20会话、36/36独立输入检查、54/54上下文负例检查通过；Laya直接完成9/20轮，其余11轮进入脚本兜底，与Mac c10一致。独立输入检查允许拒答，不表示36条都独立解决。

这些案例参与过开发或是相关的合成案例，不是全新独立盲测集。“无新增错误执行”仅限这些测试和接纳策略，不代表泛化无误触发。

## 延迟与并发

| 测量 | P50 | P95 | 最大 | 超过1秒 |
|---|---:|---:|---:|---:|
| 326次固定输入总体 | 278.83 ms | 751.76 ms | 1006.01 ms | 1/326 |
| 其中原20轮新链路输入 | 742.39 ms | 775.76 ms | 1006.01 ms | 1/20 |
| 最慢请求重复30次 | 942.52 ms | 988.53 ms | 1029.31 ms | 1/30 |

总体包含很多单问题续接输入，因此278.83ms不代表每轮新链路耗时。10秒诊断预算的动态回放110次无错误，中位数725.97ms、最大936.21ms。

实际1秒deadline下：连续20轮与轮间隔1秒的20轮均无超时/503、均9次直接完成，最大分别987.32/989.32ms。**不能因此覆盖掉另两组实测超预算结果。** 最慢情况余量不足，用户体验仍可能偶发走LLM。

并发20对：20次成功、20次503拒绝；成功请求P95 758.85ms、最大961.84ms；503最长3.67ms。符合max_pending=1的快速交还策略；跨会话同时请求不会保证两条都由Laya完成。

## 尾部原因与未采用的配置

最慢请求的五个问题长度为：intent93、device241、action135、context_device392、follow225。context_device因此落到512档。原调度把512档与一个256档问题放在同一核，另一个核运行128/256/256档。

临时启动过“两个核都支持384/512档”的配置；逐条静态调度检查发现326次请求的实际队列全部不变，因此没有用它重新跑负载，也不保留为推荐配置。[调度记录](schedules.json)。这不是已证明的性能优化。

后续若要消除长上下文尾部，应优先检查上下文表示和批量问题调度成本，并重新验证接纳决定；本轮没有缩短默认历史、提高deadline或降低阈值来改变测试结果。

## 复跑与交付

`requests.jsonl` 是本轮冻结的完整请求及参照，无需训练目录即可复跑板端probe。`prepare.py` 记录来源组装方法；原验收来源在c10历史证据包中。服务、probe和analyze脚本保留在本目录，不能直接替换生产服务。

1. 在有RKNN Toolkit 2.3.2的环境，用现有`laya_npu.py convert`转换固定c10导出的ONNX；核对本目录哈希。
2. 在独立端口启动`run_service.py --root <隔离目录>`，隔离目录包含model、src、deploy；环境需当前Models依赖。
3. 板端运行`probe.py --requests requests.jsonl --out <输出目录>`；用Agent/SDK环境运行`analyze.py --responses <responses.jsonl> --out <decisions.json>`。
4. 用更新后的`../model-first-20261008/replay.py`运行动态回放，分别指定`--timeout-ms 10000`及`--conversation-only --timeout-ms 1000`，间隔测试加`--turn-gap-ms 1000`。
